# Repository delivery instructions

For AI-EFFECT service parameterisation and Design with AI release work, use the current [production delivery plan](https://github.com/IRESI-EU/ai-effect-solution-studio/blob/main/docs/PRODUCTION_DELIVERY_PLAN.md) as the delivery baseline.

- Read the plan, latest checkpoint log and previous failed/blocked evidence before choosing work. On older development worktrees, retrieve the current main-branch document rather than relying on stale chat summaries.
- R1 manual configuration -> explicit Run -> associated results is the active release priority. Identify the checkpoint and observable user outcome at the start of each pass.
- Carry unresolved release blockers forward. Do not silently divert into later-release features, unrelated UI, additional demonstration harnesses or new frameworks.
- Preserve dirty work, historical failures, saved designs/results, retained demonstrations and closed spending ledgers.
- Complete authorised reversible implementation and relevant checks when possible. Documentation alone is not a passed release milestone.
- Update the canonical plan's tracker and append a checkpoint entry with exact source/running version, fresh evidence, blockers/owners and schedule impact. If this worktree cannot update main, publish a linked checkpoint record and flag canonical-tracker synchronisation as pending; do not claim it happened.
- End every delivery pass with: What worked? What failed? What can I demonstrate now? What specific problem are we tackling next?
- Keep implemented, locally verified, staging verified and production verified distinct. Mark a checkpoint PASSED only with its required evidence; mark a release RELEASED only after actual authorised deployment and verification.
- Dates are targets pending CP01 confirmation. Record slips and reasons openly.
- New explicit user instructions take precedence; record resulting scope decisions. Routine reversible work does not require a new permission request just because the plan changes.
- This plan supplies no new metered-call or production-cutover authority. Respect concrete approved limits and keep closed scopes closed. The daily 8 am automation stays paused.

For unrelated repository tasks, follow the task's own scope and the applicable instructions. Do not reinterpret this release plan as authority to change production.
