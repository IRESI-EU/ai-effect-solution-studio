## Schema and data preservation

The observed 22 November production schema has seven application tables, no `solutions.design_metadata`, no execution submissions/receipts and no local-capture or AI draft tables. The current candidate cannot read saved solutions correctly without the existing additive migration bundle.

`DATABASE_SCHEMA_MODE=validate` is required by the R1 API image/overlay. Startup checks model columns, unique workflow association and receipt identity without issuing DDL. It fails with a migration-required message instead of silently creating tables. Default `create` remains only for existing compatibility/local tooling; this is not the R1 release setting. R1 also leaves account bootstrap/fixture seeding empty.

After separately authorised backup/restore and operator review, migrations `003_design_ai_pilot.sql`, `004_instance_submissions.sql`, `005_local_capture_records.sql` are the required existing additive bundle. 001/002 are already represented in the observed schema; do not replay historical ownership/node rewrites indiscriminately. Apply with ON_ERROR_STOP and reviewed transaction boundaries (005 has its own BEGIN/COMMIT). Retain columns, history and ownerless records on application rollback. Never drop evidence tables to run an older binary.

Focused PostgreSQL checks in `tests/test_r1_postgresql.py` require a fresh loopback `r1_cp01` database and `r1_operator` test role. They create distinctly named small synthetic databases, retain them for inspection, and never reset/drop another database or submit a workflow. `fixtures/production-schema-20261122.sql` is schema only; no production rows, accounts, credentials, designs or data were copied. It omits pg_dump's per-dump restrict markers for driver loading. Tests use existing pytest/SQLAlchemy/psycopg tooling.
