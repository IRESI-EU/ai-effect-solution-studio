## Actual behavior, not local qualification-wrapper assumptions

**Generator HTTP control:** ExecuteRequest declares method, workflow_id, task_id and inputs. There is no parameters field or http-parameters-v1 validation route in the inspected interface. ConfigureAndSynthesize internally calls ConfigureGrid and then SynthesizeGrid. With no input it uses three source-defined level specifications, inter-level connection specifications, seed 42, loading M and ref_sys_id 1. Its first input may be inline base64 JSON containing level_specs, connection_specs, seed, loading_level and ref_sys_id. Malformed or non-inline configuration silently becomes an empty configuration/defaults. No complete, strict numeric bounds contract is exposed. The direct gRPC GridSynthesisRequest has level_specs, connections, int32 seed, loading_level, ref_sys_id and metadata; the handler forwards positive seeds such as 43. This is static source evidence, not a seed-43 run or owner qualification.

The existing composer emits flat instance settings through http-parameters-v1. Sending seed=43 there would not prove consumption: this deployed HTTP model has no such field. The drafts therefore do not invent execution_parameters or the local wrappers' seed enum [42,43]. A narrower optional-inline configuration contract is described separately from any future approved flat setting transport.

Observed level defaults (n, avg_k, diam, dist_type, max_k) are (20, 3.0, 6, dgln, 15), (60, 2.2, 10, dgln, 10), and (100, 2.0, 15, dgln, 10). The two default inter-level k-stars connections are 0->1 with c=0.174/gamma=4.15 and 1->2 with c=0.150/gamma=4.15. These are observed defaults, not owner-approved safe bounds or AI-selectable settings. The positive int32 gRPC seed forwarding rule and the inline JSON behavior differ for zero/negative/malformed values; supported library bounds still need owner confirmation.

**Generator output:** HTTP control emits DataReference(protocol=grpc, format=GetGridData), pointing to its data service. Its canonical GetGridDataResponse contains success/message and GridData with pandapower_json, grid_id, seed, loading_level, ref_sys_id, source_config and metadata. It does not emit a captured_grid slot/file. GetGridData takes an empty request and returns a process-wide cached latest grid. That reference does not by itself identify an immutable workflow/task snapshot.

**Benchmark HTTP control:** at least one input is required. A grpc input calls the upstream DataSynthesizerService.GetGridData; inline or HTTP(S) input supplies optional benchmark/algorithm JSON. Multiple inputs and these alternate branches exist in the general API. For the proposed narrow two-operation profile only one upstream grpc reference and built-in defaults are proposed, subject to owner approval. Defaults observed in source: max_steps 200, environment synthetic-grid-v0, time_series_ids [0] and bundled algorithms/algorithm_template.py. Optional configuration includes KPIs, scenarios/topology/time-series/backend and algorithm source bytes/text/URI; none of these untrusted code/path inputs is proposed as an AI-selectable beta setting. The service adapts fetched GridData internally, including a static time-series fallback. Its output is a grpc GetBenchmarkResult reference to a cached canonical structured result.

Direct gRPC RunBenchmark instead takes BenchmarkExecutionSpec (config, algorithm, input_kind, grid_data/artifacts, metadata). Forwarding the generator's protobuf response directly into that request would be a shape mismatch. The actual **HTTP-control reference path is different**: it can fetch the upstream grid. A contract may only attest that path after its protocol, schema, cardinality, content type and bounded defaults are confirmed. Native/control registration flags alone do not declare whole-output-v1 support or scientific qualification.
