## Conversation policy

The saved-solution prompt distinguishes information, sufficiently specified design, unresolved design choice, explanation and unsupported capability. Information does not force a workflow or optional-setting question. Sufficient design information should produce a useful proposal. Material choices and ambiguous instances require a focused question; a supported low-impact reversible assumption is an acceptable alternative when clearly disclosed before Apply. Published defaults are not scientific approval or proof that a goal is satisfied. In particular, a one-candidate maximum does not support comparing multiple layouts.

The policy contains no service-specific IDs, names, acceptance sentences or prepared answers. It preserves the goal and pending question across explanations and short replies. It requires partial parameter edits, separate input selection, explicit reviewed Apply/Save and separate Builder Run. Semantic intent selection and honesty of proposed assumptions are still model/human-review questions, not guarantees from schema validation.

## Focused response and existing editor

`SavedSolutionResponse` has five fields: `outcome`, `message`, `clarification`, `solution_edits`, `assumptions`. Outcomes are `answer`, `clarification`, `proposal`, `unsupported`. Strict validation rejects extra/legacy fields, blank messages/questions/assumptions, edits on a non-proposal, an empty proposal, a question on another outcome and assumptions outside a proposal. Parsed model instances are revalidated too. Supported edits reuse `SolutionEdit`; the existing candidate validator remains authoritative for values, targets, contracts, ownership and compatibility.

The saved-solution router strictly validates this response, then uses a small explicit adapter into the existing `AssistantTurn` review engine. It does not parse a legacy answer as a fallback. Legacy routes still select their existing schema and prompt. A recorded legacy failure is explicitly translated only in its offline state-preservation replay, retaining its actual text and no clarification; the historical response file is unchanged.

Proposed assumptions are stored in the ordinary pending change review, ahead of the design changes, with an explicit notice that they are proposed choices rather than prior user instructions or scientific approval. They survive reopening and explanatory detours. They never become graph nodes, parameter values or input data. Conversation records retain the focused outcome and assumption disclosures. Existing Apply/Save/Undo, version/authority checks, compiler and Run transport remain the single editing/execution path.

Dispatch and SDK parsing select the focused response only for the server-owned saved-solution context. Every accounting backend now calculates its conservative input bound from that exact selected SDK wire format, including its strict schema/name and framing. Audit format 4 hashes the selected strict wire schema and actual validated focused response before adaptation. The installed SDK's conversion differs from ordinary Pydantic JSON Schema; captured offline HTTP verifies equality with what the SDK actually sends. The focused format is 1,453 JSON bytes versus 3,499 for the legacy format in the installed SDK, with the same conservative accounting limits. The internal SDK converter is pinned by `openai==2.54.0`; upgrades require rechecking the wire test.
